# AGENTS.md

Инструкции для ИИ-агентов, работающих с репозиторием `bb-zcode` — плагином bb,
который запускает сессии ZCode CLI внутри bb.

## Контекст проекта

- Плагин — адаптер между протоколом bb provider bridge (v2, дельты v3) и
  нативным протоколом ZCode CLI (v1, stdio). Один дочерний процесс ZCode на
  поток; настройки и возможности провайдера объявлены в `server.ts`.
- Правила контрибуции — в [CONTRIBUTING.md](CONTRIBUTING.md): только публичные
  поверхности SDK, сфокусированные тесты для изменений протокола, lifecycle и
  approvals, `npm run marketplace:build` после изменения брендинга или
  `PLUGIN_OVERVIEW.md`.
- Основные команды: `npm run check` (marketplace:check + typecheck + test +
  build; для build нужен CLI bb или `bb-app@0.46.1`), `npm run format:check`,
  `npm run test:live` (живой CLI с изолированным loopback-фикстуром; полный
  bb-smoke — только на одноразовом инстансе bb).
- Архитектура и границы проверяемости: [docs/capability-audit.md](docs/capability-audit.md)
  и [docs/validation.md](docs/validation.md).

## Использование базы знаний

База инженерных знаний лежит в [`knowledge/`](knowledge/) в формате
[OKF v0.2](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/ad30107c31c06aec8a7d5636e0d1058118604e6f/SPEC.md).
Она дополняет README и `docs/`, а не дублирует их.

### Перед существенной задачей

- Прочитать [`knowledge/index.md`](knowledge/index.md) и выбрать документы,
  относящиеся к задаче. При необходимости искать по `knowledge/` через `rg` и
  переходить по ссылкам.
- Не загружать весь корпус без необходимости.
- Проверять `status`, `stale_after` и основания в `verified` каждого
  документа. Просроченные сведения перепроверять по первоисточникам;
  `deprecated`-документы учитывать как историю, а не как текущее поведение.

### Во время работы

- Критичные утверждения сверять с текущим кодом, тестами и конфигурацией,
  а не полагаться на память или на текст документа.
- При расхождении знаний и кода установить, что устарело или нарушено, и
  зафиксировать вывод; не выбирать версию «автоматически» — код, тесты и
  документация должны прийти к согласию в рамках одного изменения.
- Отделять подтверждённые факты от гипотез; непроверенное помечать как
  предположение и не оформлять со статусом `stable`.

### Перед завершением задачи

- Оценить, появились ли устойчивые знания: принятое решение, инвариант,
  ограничение, причина ошибки, проверенная процедура.
- Обновить существующий документ базы либо создать новый со ссылками на
  основания (код, тесты, ADR/история). Большие README и `docs/` не
  дублировать — ссылаться на них.
- Если изменение затрагивает поведение, обновить связанные документы базы в
  том же PR: архитектуру, контракты, инварианты, runbook'и.
- Поддерживать `knowledge/index.md` и внутренние ссылки в актуальном
  состоянии; записи об обновлениях добавлять в `knowledge/log.md`.
- После существенной правки пересмотреть прежние записи `verified`: убрать
  или переоформить те, что больше не подтверждены; неподтверждённые сведения
  переводить в `status: draft`.
- Не сохранять рутинный пересказ сессии и дубликаты.
- В итоговом отчёте указать обновлённые документы базы либо явно отметить,
  что обновление знаний не требовалось.
